# Issue #3 — [incident] Массовая рассылка приглашений коллегам при синхронизации календаря

> Archived from GitHub Issues before the repository was recreated for public release.
> State: OPEN · created 2026-07-18T20:59:36Z

## Что произошло

При синхронизации календаря по коллегам ушла массовая рассылка приглашений/обновлений **от имени пользователя**. Письма получили реальные люди — репутационный и операционный ущерб.

## Радиус и корневая причина

Инцидент — произведение двух факторов:

1. **Полный синк вместо окна.** Первый подход (`vdirsyncer`) синхронизировал **всю коллекцию Exchange без временного окна** — обрабатывались события за всё время существования календаря. Это и есть «синхронизация всех мероприятий за ВСЕ время».
2. **Механизм рассылки.** `vdirsyncer` загружал в Google **структурные свойства `ATTENDEE`**, а Google Calendar при create/update таких событий **автоматически шлёт приглашения адресатам**. Дополнительный вектор — write-back в Exchange по организованным встречам рассылает update/cancel от организатора (то есть «от моего имени»).

**Полный охват × авторассылка = массовый спам.** Узкое окно тут — не про «не слать письма», а про **ограничение радиуса**: даже одна регрессия на ±7-дневном окне заденет десятки адресатов, а не весь календарь.

## Текущее состояние (важно)

- `vdirsyncer` уже **заменён** кастомным `syncer/sync.py`: окно −7…+90 дней, `ATTENDEE`/`ORGANIZER` срезаются в текст описания, запись в Google с `sendUpdates=none`, в Exchange не пишет вообще. **Механизм рассылки в текущем коде закрыт.**
- В `docker-compose.yml` сервиса `vdirsyncer` нет (только `davmail` + `syncer`).
- **Остаток:** на диске лежит vdirsyncer-state `state/status/` (`mtswork.collections` + `mtswork/mtswork.items`, ~987 KB). Инертен без бинаря, но должен быть удалён.
- Запрошено пользователем: сузить окно до **±7 дней** (1 неделя назад + 1 неделя вперёд). Сейчас `WINDOW_FUTURE_DAYS=90`.

## Защита в будущем (defense-in-depth)

Порядок по приоритету. **Гарантия «письма не уходят» = слои D2–D4** (окно их НЕ даёт). **Окно D1 + guard D5** ловят runaway / «полный синк» и ограничивают радиус.

- **D1. Узкое окно ±7.** `WINDOW_FUTURE_DAYS: 90 → 7` в `docker-compose.yml` и дефолт в `syncer/sync.py` (`WINDOW_PAST_DAYS` уже 7). Ограничивает радиус любой ошибки.
- **D2. Никаких структурных `attendees`/`organizer` в Google — на КАЖДОЙ записи.** Сейчас проверка `assert "attendees" not in ev` живёт только в ветке `DRY_RUN` (`syncer/sync.py:255`). Перенести в `upsert()` как жёсткий инвариант: любой payload с этими ключами → **abort всего запуска до записи**.
- **D3. `sendUpdates=none` на всех POST/PUT/DELETE.** Уже есть (`syncer/sync.py:222,227,278`). Закрепить тестом, чтобы не регрессировало.
- **D4. Источник строго read-only.** Синкер делает к Exchange/DavMail только `REPORT` (чтение), ни одного write. Убрать из репозитория любые следы обратной записи (упоминание «vdirsyncer storage» в `secrets/exchange_password.example`).
- **D5. Runaway-guard.** Если число событий в окне > CAP (например 250) — **abort без единой записи** + лог с числом. ±7 дней = десятки событий; сотни означают, что окно/фильтр сломались («полная история») — не писать вслепую.
- **D6. Kill-switch.** `SYNC_ENABLED` (по умолчанию выкл до явного подтверждения) либо дефолт `DRY_RUN` при первом старте новой конфигурации.
- **D7. Полностью выпилить vdirsyncer.** Удалить `state/status/`, убрать упоминание из `secrets/*.example`, чтобы его нельзя было случайно запустить — это единственный компонент, умеющий слать письма.

> Смежно (тот же класс «сломанное чтение → массовое действие»): пустой или частичный ответ Exchange не должен приводить к массовому удалению в Google через reconcile. Отдельный дефект, но лечится в связке с D5.

## Критерии приёмки

- [ ] Окно синка −7…+7 (`WINDOW_FUTURE_DAYS=7`).
- [ ] Тест: ни один payload на запись не содержит `attendees`/`organizer`; нарушение роняет запуск **до** обращения к Google.
- [ ] Тест: все write-вызовы к Google несут `sendUpdates=none`.
- [ ] Синкер не выполняет ни одного write в сторону DavMail/Exchange (только `REPORT`).
- [ ] Guard: `fetch > CAP` → abort без записей, в логе число событий.
- [ ] Остатки vdirsyncer удалены (`state/status/`, пример в `secrets/`); запустить vdirsyncer из репозитория невозможно.
- [ ] README: в шапке — как за 10 секунд остановить синк (`docker compose stop syncer`).
